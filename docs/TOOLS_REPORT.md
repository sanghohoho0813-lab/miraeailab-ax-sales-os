## 3. 4대보험 명부 — 개인정보 경계

명부의 한 줄은 그 자체가 한 사람의 개인정보입니다. 그래서 이 파서는:

- 이름·주민번호·생년월일을 **읽지도 저장하지도** 않는다
- 근거(`sourceText`) 에 명부 원문을 남기지 않는다 — "4대보험 명부 N행 집계 (개인정보는 저장하지 않음)" 고정 문구만
- 날짜를 읽기 **전에** `scrubPii()` 로 주민번호를 지운다

테스트가 이것을 증명합니다 — 단위·E2E 양쪽에서 주민번호 패턴·이름이 화면·근거·`localStorage` 어디에도 없어야 통과합니다.

### E2E 가 잡은 실제 버그

명부 파싱에서 **주민번호가 날짜 파싱을 망가뜨리고 있었습니다.**

```
"홍가상 900101-1234567 2019-03-04"
  날짜 정규식이 주민번호 안에서 "900101-12" 를 먼저 집어
  → 진짜 취득일 2019-03-04 을 건너뛴다 → 가입자 5명이 1명으로
```

단위 테스트는 제가 지어낸 줄(공백 **두 칸**)을 써서 정규식이 우연히 통과해 이 버그를 놓쳤습니다.
브라우저가 실제로 만드는 줄은 공백 **한 칸**이었고, E2E 에서만 드러났습니다.

고친 것 둘:
1. 날짜를 읽기 전에 `scrubPii()` — 파서가 주민번호를 애초에 보지 않는다(원칙)
2. 날짜 정규식에 앞뒤 경계(`(?<![\d\-.])` … `(?![\d])`) — 숫자열 한가운데를 날짜로 읽지 않는다(정확성)

그리고 **단위 테스트의 픽스처를 브라우저 실제 출력으로 교체**했습니다. 지어낸 입력으로 테스트하면 이런 버그를 또 놓칩니다.

## 4. 정책자금 유력 기관 — "승인 가능성" 이 아니라 "실제로 누가 댔나"

리서치 사례 371건의 조달 형태(`fundingForm`)·프로그램(`policyPrograms`) 에서 기관을 셉니다.
같은 업종을 먼저 보고, 기관별로 근거 사례를 최대 3건 붙입니다.

**이 사례 DB 의 한계를 화면에 그대로 적습니다:**

- 371건 중 **203건이 민간투자**입니다. 기관이 적힌 사례는 100건 남짓이고 대부분 창업 초기 트랙
  (신보 퍼스트펭귄·리틀펭귄, TIPS, 청년창업사관학교) 입니다.
- 업력이 긴 일반 중소기업의 **기보·신보 일반보증, 중진공 융자, 소진공 자금 사례는 거의 없습니다.**
- 그래서 업력 7년이 넘는 회사에는 "창업 초기 전용 프로그램이 섞여 있다 — 기관은 같아도 창구가 다르다" 고 경고합니다.
- 항상 마지막에: **"이 목록은 실제 사례에 나온 기관이고 신청 자격·한도·심사 기준이 아닙니다."**

억지로 채우지 않습니다 — 기관이 확인된 사례가 없으면 "사례에서 확인된 기관이 없습니다" 가 정답입니다.
